# 提示词分层与多轮历史：设计、风险与上线计划（S6）

状态：**设计稿，未实现，等用户确认上线时机（U3）**。本文不改任何行为。
影响范围：所有对话接口（流式与非流式、所有模型），即全部用户的回复质量。

## 1. 现状（以代码为准）

- `BaseChatHandleProxy#getPrompt` 把"角色正文 + Requirements + NOTE + 历史文本"拼成**一条 user 消息**。
- 历史是 `[user]...\n[assistant]...` 文本，由服务端 `ChatHistoryService#promptHistory` 取最近 30 条生成（缓存 60 条）。
- 流式与非流式都只发两条消息：`system`（各 handler 写死的一句话）和 `user`（上面那一大段）。
- 旧模板里有写死的 `# Example`（"我叫小爱"），对所有旧人设生效。

## 2. 目标结构

```
system : 平台规则（语言、安全边界、输出格式），角色不可覆盖
system : 角色（人设正文，放在明确的分隔块里，限制长度）
messages: 最近 N 轮历史，用原生 role/content 多轮（user / assistant）
user   : 当轮新消息
```

长期记忆（mem0）与会话摘要不在本次范围内，按分析文档 4.1 另立。

## 3. 收益

- 模型对"哪句是用户说的、哪句是自己说的"的判断更稳，减少把 `[assistant]` 标记回显进正文的情况（这是现在要靠 `cleanAssistant` 补丁的原因）。
- 角色正文与平台规则分层，降低用户自建角色覆盖规则的风险。
- 去掉写死的 `# Example`，旧人设不再被塞入"我叫小爱"。

## 4. 风险

| # | 风险 | 说明 | 缓解 |
|---|---|---|---|
| R1 | 回复风格整体变化 | 所有模型对同一人设的语气可能不同，用户会感知为"变笨/变了" | 先灰度（见第 5 节），对比一周的人工抽样 |
| R2 | 上游协议差异 | Gemini 的 `contents` 结构、Qwen（DashScope）、Doubao 的 SDK 对 system/多轮的支持不同 | 逐 handler 确认；Gemini 与 SDK 类先保持旧路径 |
| R3 | token 成本与截断 | 多轮比单段文本更占 token 位置上的开销；`max_tokens` 与上下文上限要重算 | 历史轮数上限 + 按 token 估算截断，超限丢最旧轮 |
| R4 | 历史截断边界 | 按轮截断时可能切断一对 user/assistant，或留下孤立的 assistant | 截断按"轮"成对进行，首条必须是 user |
| R5 | 空回复与部分回复进入历史 | 已有规则：空回复不落库，取消时保存部分文本；多轮后部分文本会被当成完整回复继续推理 | 被取消的部分回复保留但标记（需新字段或 content 前缀），或只在 UI 提示 |
| R6 | 角色正文里的 `%` 与格式 | 旧路径有 `String.format` 风险（已在目录角色路径修掉） | 全部改为拼接，不再使用格式化 |
| R7 | 客户端行为不变 | 客户端协议不变（仍只发 sessionId + text），风险只在服务端 | 无需客户端同步发版 |
| R8 | 回归难发现 | 没有自动化对话质量测试，只能靠抽样 | 上线前准备固定的 30 条对话样本，人工对比 |

## 5. 上线计划（建议，等用户确认）

1. **准备（不影响线上）**：实现分层构造函数，保留旧 `getPrompt` 作为默认；新路径由开关控制（配置项，默认关）。
2. **样本对比**：固定 30 条对话（覆盖目录角色、旧人设、自建角色、长历史、中文/英文），分别用两种结构各生成一遍，人工打分。
3. **灰度**：按用户 id 取模开 5%，观察 3 天：空回复率、取消率、用户重新生成率（代理指标）、错误日志。
4. **全量**：指标不劣于旧路径后再全量；保留开关 7 天以便一键回退。
5. **清理**：稳定后删除旧 `getPrompt` 的拼接分支与 `cleanAssistant` 补丁（仍保留对输出的兜底清理，直到确认模型不再回显标记）。

回退：关闭开关即可，不涉及数据迁移（历史存储不变）。

## 6. 需要用户决定

- U3：上线时机（是否与客户端发版同期，还是先于客户端）。
- 灰度比例与观察窗口是否接受以上默认值。
- 自建角色是否限制长度（建议限制，具体数值待定）。
